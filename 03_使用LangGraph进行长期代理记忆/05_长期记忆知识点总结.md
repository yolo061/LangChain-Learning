## 一、课程主线：一个邮件助手，四种记忆

课程自始至终只做一个东西：**邮件助手**。收到一封邮件，三选一处理——忽略（ignore）、通知（notify）、回复（respond）。每一课做的事本质相同：**把上一课"写死在代码里的东西"搬进长期记忆 store，让它可以运行时被更新**。

| 课程 | 笔记本 | 记忆类型 | 搬进 store 的东西 | 谁来写 |
|---|---|---|---|---|
| L2 基线 | 01 | （无，全部静态） | —（profile 和规则硬编码） | 开发者 |
| L3 语义 | 02 | 语义记忆 | 联系人、讨论过的事实（collection） | LLM 自己调工具 |
| L4 情景 | 03 | 情景记忆 | 历史邮件 + 分类结果（examples） | 代码 store.put 轨迹 |
| L5 程序 | 04 | 程序记忆 | 分类规则、agent 总指令 | 优化器（反馈闭环） |

三种记忆的准确定义：

- **语义记忆（Semantic）**：关于世界的事实。用户是谁、联系人背景、讨论过的项目细节。对应 profile 和 collection。
- **情景记忆（Episodic）**： agent 自己经历过的事。处理过的邮件、做过的决策、得到的结果。用途是"以前遇到过类似的，我上次是这么处理的"——即 few-shot 示例。
- **程序记忆（Procedural）**： agent 的行为准则——系统提示词、分类规则本身。它决定 agent "怎么做"，而且是三种记忆里唯一关于"改变 agent 行为"的。

## 二、贯穿全程的基础设施

### 2.1 InMemoryStore：键值 + 向量二合一

langgraph 的 store 是带命名空间的 KV 存储，配上 embedding 后兼做向量库。四个核心操作：

```python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore(index={"embed": "ollama:qwen3-embedding:0.6b"})

store.put(namespace, key, value)     # 写
store.get(namespace, key)            # 读单个，返回 Item（.value 取内容）
store.search(namespace, query=..., limit=...)  # 语义检索（需配 index）
store.list_namespaces()              # 列出所有已写入的命名空间
```

要点：

- **不配 `index` 时 store 退化为纯 KV**，`search` 不支持 `query` 参数。
- **`search` 没有阈值参数**（已读源码验证）：只有 `query / limit / offset / filter`，想按相似度分数过滤要拿到结果后自己筛（不带 query 时 score 为 None）。
- **namespace 是元组**，课程约定 `(应用名, 用户ID, 类别)`，如 `("email_assistant", "raojiarui", "examples")`。分层设计让"按用户清空/导出某类记忆"成为一次调用。
- InMemoryStore 是课程教学用，**接口与生产后端（PostgresStore 等）一致**，换实现不换代码——这是面试可讲的设计点。

### 2.2 用户隔离：configurable.langgraph_user_id

```python
config = {"configurable": {"langgraph_user_id": "lance"}}
email_agent.invoke({"email_input": email_input}, config=config)
```

注意：**`langgraph_user_id` 是课程自造的键，不是 langgraph 官方约定**（已源码验证）。langgraph 只要求 configurable 是个 dict，键叫什么都行——但要全链路一致：节点里取、工具模板里填、invoke 时传，三处同名。工具 namespace 里的 `"{langgraph_user_id}"` 是**模板占位符**，运行时自动替换成 config 里的值。

### 2.3 本机模型环境

- 对话模型：`init_chat_model("deepseek-v4-flash", extra_body={"thinking": {"type": "disabled"}})`——**结构化输出/工具调用场景必须关 thinking**（原因见踩坑 #5）。
- 嵌入模型：Ollama 本地 `qwen3-embedding:0.6b`。

## 三、01 笔记本：基线助手骨架

这一课没有真正的"记忆"，但搭起了后面所有课共用的骨架。

- **结构化路由**：Pydantic 扁平 schema（`reasoning: str` + `classification: Literal["ignore","respond","notify"]`），`llm.with_structured_output(Router)` 返回 Route 实例。经验：**分类/路由用扁平 schema + Literal 枚举最稳**，嵌套 class 无意义。
- **提示词组装**：`triage_system_prompt.format(full_name=..., user_profile_background=..., triage_no=..., triage_notify=..., triage_email=..., examples=...)`——注意这几扇"门"从第一课就留好了，后面每课做的事就是**改变这些槽位的来源**（写死 → store 读取）。
- **占位工具三件套**：`@tool write_email / schedule_meeting / check_calendar_availability`，只返回假结果。工具的 docstring 是给 LLM 看的说明书。
- **create_agent（v1）**：静态系统提示词直接 `system_prompt=` 参数；只有动态注入记忆才需要 `@dynamic_prompt` 中间件。
- **StateGraph 骨架**：`State = TypedDict(email_input, messages: Annotated[list, add_messages])`；`triage_router` 节点返回 **`Command(goto=..., update=...)`** 做动态路由（respond → response_agent，其余 → END）；入口用 `add_edge(START, "triage_router")`。
- 这一课所有"记忆"都是 Python 变量：`profile`、`prompt_instructions`——它们就是后面课程要搬进 store 的东西。

## 四、02 笔记本：可管理的语义记忆

核心升级：**LLM 自己获得读写记忆的工具**，开发者不再预设它该记什么。

```python
from langmem import create_manage_memory_tool, create_search_memory_tool

manage_memory_tool = create_manage_memory_tool(
    namespace=("email_assistant", "{langgraph_user_id}", "collection")
)
search_memory_tool = create_search_memory_tool(
    namespace=("email_assistant", "{langgraph_user_id}", "collection")
)
```

- 把这两个工具加进 create_agent 的工具列表，LLM 就能在对话中自主存/查事实（"这位联系人负责支付系统"→ 存；下次遇到 → 查）。
- **`@dynamic_prompt` 中间件**：每次调用前动态组装系统提示词，从 store 实时读取 `instructions`，实现"提示词即记忆"的读通路。要点：返回值必须是 **str**；v1 中间件签名是**单参数 request**（拿 state/config/store 都从 request 里取）。
- `store.list_namespaces()` 是调试利器：确认 LLM 到底把记忆写到了哪个空间。
- `search` 带 `query` 是语义检索，不带则返回该空间全部条目。

## 五、03 笔记本：情景记忆（few-shot 化的经历）

核心升级：**把完整轨迹（邮件+分类结果）存下来，检索相似经历反哺分类提示词**。

```python
# 写入：一封邮件 + 它的分类结果，作为一个"情景"
store.put(
    ("email_assistant", user_id, "examples"),
    str(uuid.uuid4()),
    {"email": email, "label": "respond"},
)

# 读取：遇到新邮件，检索最相似的旧情景
results = store.search(
    ("email_assistant", user_id, "examples"),
    query=str({"email": new_email}),   # 把邮件 dict 序列化成字符串做查询
    limit=1,
)
```

- `format_few_shot_examples()`：把检索到的 Item 列表套进模板（Subject/From/To/Content + 分类结果），拼成文本塞进 triage prompt 的 `<Few shot examples>` 区。
- 提示词里那句 **"Follow these examples more than any instructions above"** 是点睛之笔：示例的优先级高于文字规则。
- 与 02 的本质区别：02 是 LLM **主动**存零散事实；03 是系统**被动**存完整轨迹，用嵌入相似度检索——"见过类似的就这么分"。
- 实现细节：情景的写入是 `store.put`（代码控制），检索发生在 triage_router 节点内——读写通路分离。

## 六、04 笔记本：程序记忆（prompt 即记忆）

核心思想一句话：**agent 的行为准则本身也放 store，用反馈自动改写**——"prompt 即记忆，optimizer 即写入头"。

### 6.1 懒播种（lazy seeding）

节点里对每个记忆键做 get → None 则 put 默认值的兜底：

- `triage_router` 播种 `triage_ignore / triage_notify / triage_respond`（namespace 是 `(用户ID,)`，用户级）；
- `create_prompt` 中间件播种 `agent_instructions`。

首次见到某用户自动初始化，之后每次实时读取。**注意播种的 key 与后续读取的 key 必须完全同名**（踩坑 #6）。

### 6.2 store 注入机制

- 节点签名加 `store` 参数即可拿到 store——**按参数名匹配**：名为 `store` 的参数无标注也注入；要标注必须标 `BaseStore`，标 `InMemoryStore` 反而匹配失败。
- 忘了 `compile(store=store)` 是此类报错的头号根因：无 store 可注入时，该参数被整个省略，报 "missing 1 required positional argument: 'store'"。

### 6.3 优化器闭环（本课压轴）

```python
# ① 组装待优化清单：prompt 从 store 实时读，附上元信息
prompts = [
    {"name": "main_agent", "prompt": store.get(("lance",), "agent_instructions").value['prompt'],
     "update_instructions": "keep the instructions short and to the point",
     "when_to_update": "Update this prompt whenever there is feedback on how the agent should write emails"},
    # ... triage-ignore / triage-notify / triage-respond 同构
]

# ② 组装原料：轨迹 + 用户反馈
conversations = [(response['messages'], "Ignore any emails from Alice Jones")]

# ③ 构造优化器（传模型实例，不是字符串！）
optimizer = create_multi_prompt_optimizer(
    init_chat_model("deepseek-v4-flash", extra_body={"thinking": {"type": "disabled"}}),
    kind="prompt_memory",
)

# ④ 优化：内部先跑分类器决定改哪几条，再逐条改写
updated = optimizer.invoke({"trajectories": conversations, "prompts": prompts})

# ⑤ 写回：只写真正变化的；name → store key 用映射表
NAME_TO_KEY = {
    "main_agent": "agent_instructions",
    "triage-ignore": "triage_ignore",
    "triage-notify": "triage_notify",
    "triage-respond": "triage_respond",
}
for i, updated_prompt in enumerate(updated):
    if updated_prompt["prompt"] != prompts[i]["prompt"]:
        name = prompts[i]["name"]
        store.put(("lance",), NAME_TO_KEY[name], {"prompt": updated_prompt["prompt"]})
```

三个元信息字段各司其职：

- `prompt`：当前值（从 store 实时读，改过的地方自动累积）；
- `update_instructions`：改写风格约束（"保持简短"）；
- `when_to_update`：**反馈路由依据**——告诉优化器什么反馈才归这条管（建议，非硬约束，见踩坑 #8）。

`kind` 两种模式：`"prompt_memory"` 直接输出累积了教训的新 prompt（prompt 即记忆，课程用的就是这个）；`"reflection"` 先输出反思推理再改写（适合调试观察）。

为什么 multi：4 条 prompt 是联动团队（"忽略 Alice 的邮件"可能同时涉及 triage-ignore 和 triage_respond），一起审视才能改得一致；单条各自优化会互相冲突。

## 七、踩坑实录（全部真跑出来的）

1. **START/END 是保留伪节点名**：`ValueError: Node __start__ is reserved`。设入口用 `add_edge(START, 节点名)`，不是 `add_node`；store 只传给 `compile(store=store)`。
2. **store 注入按参数名**：名为 `store` 的参数无标注也注入；标 `InMemoryStore` 反而注入失败，要标就标 `BaseStore`。报 missing 'store' 先查 `compile()` 传没传。
3. **@dynamic_prompt 不能挂实例方法**：v1 中间件只传一个 request，实例方法的 self 会占掉 request 的位置 → TypeError；必须用工厂函数/闭包，返回值必须是 str。
4. **langmem 优化器不透传参数**：`create_multi_prompt_optimizer` 签名只收模型字符串或实例，传 `extra_body=` 报"没有该字段"。**通用套路：凡库只收模型字符串又不透传参数，自己构造实例传进去**（显式构造优于字符串透传）。
5. **DeepSeek thinking 模式 vs 强制 tool_choice**：langmem 用 trustcall（强制工具调用 + 校验重试）做结构化抽取，thinking 模式下 DeepSeek 服务器禁止强制 tool_choice → 400 "Thinking mode does not support this tool_choice"。修法：关 thinking。
6. **记忆键三处一致**：播种 put 的 key、节点读的 key、prompts 列表 get 的 key 必须同名（"notify" vs "triage_notify" 事故）；命名空间的**用户 ID 也要一致**（examples 播种在 raojiarui、检索在 lance → 永远查不到，静默失效）。另外 get/put 兜底块若嵌错缩进（套进上一段 else），会静默把 A 规则赋给 B 变量——不报错但分类悄悄错。
7. **if/if/else 陷阱**：`else` 只属于**最近的同缩进 if**。两个平行 `if` + 一个 `else`，第一个 if 命中后第二个仍判定失败触发 else。多分支互斥必须用 `elif` 链。（官方 cell 33 原版就埋着这个雷。）
8. **优化器越界**：`when_to_update` 只是建议，内部路由分类器本身是 LLM，可能把不相关 prompt 也改了。处理流程：先打印 diff 看改了什么 → 判定不该动的**跳过不写回**（不 put = 改动自动丢弃，下轮 store 重读自动恢复）→ 保留日志，拒绝静默。
9. **优化器调试三板斧**：先组装 `optimizer_input` 打印检查（messages 是对象，要 `pretty_print()`）；用 `optimizer.stream()` 代替 `invoke` 看逐节点中间输出；`optimizer.get_graph().print_ascii()` 看图结构。

## 八、面试话术备查

- **一句话架构**："prompt 即记忆，optimizer 即写入头"——部署后的 agent 收到用户反馈，运行时自动把反馈固化成 prompt 修改并持久化到 store，开发者不下场改代码。
- **三种记忆 = 三条写通路**：语义 ← LLM 调工具；情景 ← 代码 put 轨迹；程序 ← 优化器写回。读通路全部汇入 prompt 组装（dynamic_prompt / few-shot 注入 / 规则注入）。
- **为什么用 store 不用全局 dict**：用户隔离（namespace 分层）、语义检索（embedding index）、接口可换生产后端（Postgres/Redis）。
- **结构化输出选型**：分类用扁平 schema + Literal + `with_structured_output`；需要校验重试的复杂抽取用 trustcall 强制 tool calling。thinking 模式与强制 tool_choice 互斥是真实的服务端约束。
- **防御式写回**：只写 diff、越界跳过、name→key 映射表消灭 if/else 分支膨胀。
- **换模型的架构自由度**：主 agent 和优化器用不同模型是合理设计——写入记忆的活儿值得用好模型，且优化器不在热路径上，调用频率低。
